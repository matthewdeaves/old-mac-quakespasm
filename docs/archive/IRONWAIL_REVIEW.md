# Ironwail technique review for the QuakeSpasm-PPC port

Survey date: 2026-05-09. Source: <https://github.com/andrei-drexler/ironwail>
(commit `5a98362`, single-commit fork tree as cloned today).

## Executive summary

Ironwail's headline gains — bindless textures, multi-draw-indirect, compute-shader culling, persistent-mapped buffers, cluster-based dynamic lights — all live above GL 4.3. **Every one of those is dead on arrival** for the six-machine PPC + Lion + GMA-950 + Lion-SDK-Sequoia matrix we ship. So the review below ignores them.

What *does* port: the CPU-side reorganisations Ironwail did along the way, and which still help when the bottleneck is CPU rather than fragment fillrate. The strongest candidates are (1) flat-array static-entity efrags replacing the per-leaf linked list (`gl_refrag.c`), (2) flat-array particle pool with in-place compaction replacing the free/active linked lists (`r_part.c`), (3) tighter lightmap atlas packing via Morton-interleave + radix sort (`r_brush.c GL_PackLitSurfaces`), and (4) lightstyle interpolation as a small visual upgrade (`gl_rlight.c R_AnimateLight`). Honest fps expectation: candidates 1–3 are sub-1 % to ~2 % each on demo1/demo2 (which barely stress static-ent counts, particle counts, or lightmap rebuilds) but can be larger on dense maps; candidate 4 is a visual change at near-zero CPU cost.

## Recommended candidates

### 1. Flat-array static-entity efrags (medium effort)

Ironwail's [`R_AddEfrags`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/gl_refrag.c#L120) writes one count + N leaf indices into a single growing `cl_efrags[]` int array; [`R_AddStaticModels`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/gl_refrag.c#L157) iterates that array linearly each frame and tests `vis[leafidx>>3]`. Compare our [`R_StoreEfrags`](https://github.com/matt/quakespasm/blob/master/Quake/gl_refrag.c) which walks `leaf->efrags` linked lists scattered across the heap and chases `pefrag->leafnext` per node visit. The Ironwail layout is one cache-line-friendly stream-read; our layout is a pointer-chase per static entity per leaf. Plan: replace `efrag_t` allocations + `mleaf_t::efrags` field with the flat int array; rewrite `R_AddEfrags` to push count-prefixed runs; add a `R_AddStaticModels` called from `R_MarkLeaves` that fills `cl_visedicts` from the `vis[]` byte. Touches `gl_refrag.c`, `gl_model.h` (drop `mleaf_t::efrags`), `r_world.c`. Honest fps: id1 maps have ~50–200 statics, so sub-1% on demo1/demo2/demo3 — but a real win on big custom maps and a heap reduction.

### 2. Flat-array particle system with in-place compaction (small effort)

Ironwail's [`CL_RunParticles`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/r_part.c#L566) iterates `particles[0..r_numactiveparticles]` and does `particles[active++] = *p` when a particle survives, dropping dead ones implicitly. Our [`CL_RunParticles`](https://github.com/matt/quakespasm/blob/master/Quake/r_part.c) walks the `active_particles` linked list and unlinks dead entries via pointer surgery. Same algorithm complexity, but Ironwail's reads and writes are sequential. Plan: drop `active_particles`/`free_particles` globals, switch to flat `r_numactiveparticles` cursor as Ironwail does. Touches only `r_part.c` (plus `R_AllocParticle` consumers — `R_RocketTrail` etc. — but the API can stay the same). Honest fps: sub-1% on demo1/demo2 (low particle counts), maybe 1-2% on G3 during heavy gib/explosion bursts where the linked-list walk dominates `CL_RunParticles`. Cache + branch wins on G3/G4 in particular (in-order PPC dislikes pointer chasing).

### 3. Lightmap atlas Morton-interleave + radix-sort packing (medium effort)

Ironwail [`GL_PackLitSurfaces`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/r_brush.c#L324) computes a sort key `Interleave(w, h) ^ 0xffff` per surface, two-pass 8-bit radix-sorts, then `AllocBlock`s in that order. The result is fewer atlas pages and tighter packing — meaningful because *every* lightmap rebuild (per dlight, per lightstyle change) iterates pages and uploads only dirty rectangles. Fewer pages = fewer `glTexSubImage2D` calls and smaller upload working set = less APPLE_client_storage / BGRA bandwidth. We already pay the BGRA + client_storage cost per page (Phase 2.1/2.2/2.3); shrinking the page count shrinks that cost linearly. Plan: import `Interleave`/`Interleave0` from [`mathlib.c:439-462`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/mathlib.c#L439); add `GL_PackLitSurfaces` between `Mod_LoadFaces` and the existing `GL_BuildLightmaps` allocation pass; route `AllocBlock` calls through it. Touches `gl_model.c`, `r_brush.c`, `mathlib.c/h`. Honest fps: load-time win is real (Ironwail's repo claims 3+ s saved on 180-lightmap maps); per-frame win is hardest to pin down — best-case 1-2% on G4 demo3 (lightstyle-heavy), neutral on G3 (already GPU-bound on lightmap blends), neutral on Lion (GMA 950 fillrate-bound regardless of page count). Worth a smoke benchmark before committing.

### 4. `r_lerplightstyles` smooth lightstyle interpolation (small effort, visual upgrade)

[`gl_rlight.c:37`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/gl_rlight.c#L37) lerps between consecutive lightstyle samples each frame instead of stepping at 10 Hz. Has a "skip if `abs(n-k) >= 12`" guard so e1m1's flickering torch doesn't smear into a slow pulse. This costs a tiny bit more lightmap-rebuild work (any non-static surface gets re-uploaded every frame, not every 100 ms) — on G3 we'd want this gated to `default 0` because the GPU-side dlight pass is the bottleneck, and on G4 we'd want it default-off in `autoexec-sawtooth.cfg` (GeForce2 MX has no shaders, every dlight pass is a full re-blend) but possibly on for `quicksilver` / `mini-g4` where Radeon 9000/9200 has fragment-shader-class fillrate to spare. Plan: copy `R_AnimateLight` body, add `r_lerplightstyles` cvar with `default 0` engine-wide, set to `1` in the per-machine autoexec for the targets where it benches neutral. Honest fps: -0.5% to -1% G4 on dlight-heavy demos as a worst case; neutral on quicksilver/mini-g4 if the existing `r_dynamic_distance` is already trimming the pass.

### 5. (Optional) CPU-side alias batch coalescing (medium effort)

Ironwail [`R_SortEntities`](https://github.com/andrei-drexler/ironwail/blob/master/Quake/gl_rmain.c#L635) radix-sorts visedicts by `model + frame + skin` so identical models cluster. Their downstream code uses GL 3.1 instancing, but the *upstream* sort makes a fixed-function-friendly optimisation possible: when consecutive visedicts share the same model and skin, we can hoist `R_SetupAliasFrame`'s `Mod_Extradata`, the texture binds, the `glColor4f(entalpha…)` setup, the `glPushMatrix/Pop` pair around `R_RotateForEntity`, and the `glTexEnvf` mode flips. Plan: add the radix sort (~60 lines), then add a "same model as previous?" early-out in `R_DrawAliasModel` that skips redundant state changes. Touches `gl_rmain.c` and `r_alias.c`. Honest fps: real on grunt-heavy maps (e2m1, e3m4) — maybe 1-3% G3, sub-1% G4/Lion. Demo1/demo2 don't pack identical models tightly enough to show the win cleanly.

## Disqualified techniques

- **Bindless textures** — requires `ARB_bindless_texture`; not exposed on Rage 128 / GeForce2 MX / Radeon 9000-9200 / GMA 950, and our 10.7-SDK Lion binary on iMac-2019 still links fixed-function paths.
- **Multi-draw-indirect** — `glMultiDrawElementsIndirect` is GL 4.3+; none of our targets have it.
- **Compute-shader frustum/PVS culling** — GL 4.3+ compute; same story. Our R_CullBox/R_MarkLeaves stays CPU-side.
- **GPU-driven dynamic light cluster pass** — same GL 4.3+ blocker. We already have `r_dynamic_distance` (Round v5 B1) doing the equivalent CPU triage.
- **Persistent-mapped buffer ringbuffer** — needs `ARB_buffer_storage` (GL 4.4); on PPC we use `APPLE_vertex_array_range` for the same purpose, on Lion/iMac-2019 we use orphan-and-respecify.
- **OIT (order-independent transparency) via per-pixel linked lists** — needs SSBO + image-load-store (GL 4.2+).
- **`gl_softemu` palettization with dithering** — fragment shader; could be done CPU-side as a postprocess, but at ≥640×480 the per-pixel cost would tank G3/G4 framerates. Skip.
- **Real-time particle vertex generation in vertex shader (`particles[oit][dither]` program)** — GLSL only; our particle path stays CPU-side billboard generation.
- **GLSL water-warp + new sky shader** — already partly addressed via our `r_oldwater 1` fallback on Rage 128 and the engine's existing GLSL sky path on Radeon 9000+.
- **Reverse-Z** — `glClipControl` is GL 4.5; the precision-improvement story is irrelevant on 16-bit-depth-buffer GPUs anyway.
